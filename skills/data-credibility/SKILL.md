# Data credibility skill (v1)

A single, versioned contract that answers three questions for every external fact:

1. **Where did it come from?** (`sourceType`, `sourceNote`)
2. **When was it observed?** (`observedAt`)
3. **How much should we trust any conclusion built on it?** (`credibility`, `confidence`)

The same contract is used by:
- the deterministic calculators in `lib/credibility.js` and `lib/intel.js`,
- the HTTP endpoints `POST /api/intel/{score,compare,prices}`,
- the model prompt block in `lib/prompt.js` (`CREDIBILITY_PROMPT_BLOCK`) used by `POST /api/intel/interpret`.

Never describe data as "verified" unless it satisfies the verified rule below.

## 1. Data contract

Every externally sourced entry (competitor, price point, cost estimate) must carry:

```json
{
  "price": 100,
  "sourceType": "official_store",
  "sourceNote": "https://example.com/item/123",
  "observedAt": "2026-10-01"
}
```

| Field | Type | Rules |
| --- | --- | --- |
| `sourceType` | enum | one of the six values below; unknown values collapse to `unknown` |
| `sourceNote` | string | URL, order number, screenshot name, or short note; max 200 chars |
| `observedAt` | string | ISO date (`YYYY-MM-DD`); required for "fresh" status |

### Source types and base weights

| `sourceType` | Meaning | Weight |
| --- | --- | --- |
| `official_store` | Brand or official store product page | 0.95 |
| `merchant_record` | Your own order, test, or invoice record | 0.90 |
| `platform_search` | Platform search results or public ranking page | 0.85 |
| `third_party_tool` | Paid or free third-party data tool | 0.70 |
| `screenshot_note` | Screenshot or manual note without a link | 0.60 |
| `unknown` | No source stated | 0.35 |

### Verified rule

Data is **verified** only when `sourceType` is `official_store` or `merchant_record` **and** `observedAt` is within 30 days. Everything else must be described as unverified, estimated, or dated.

## 2. Entry credibility score (0-100)

```
entryScore = round(100 * (0.45 * sourceWeight + 0.35 * freshness + 0.20 * completeness))
```

Freshness by age: `<=7d → 1.00`, `<=30d → 0.90`, `<=90d → 0.70`, `<=180d → 0.50`, `>180d → 0.30`, missing date → `0.45`.

Completeness: price present `0.40`, source note present `0.35`, observed date present `0.25`.

**Caps:** if `sourceType` is `unknown`, or the date is missing, or the data is older than 180 days, the entry score is capped at 60 (never "high").

Levels: `high >= 75`, `medium >= 50`, `low < 50`.

## 3. Aggregate credibility (a data set)

```
aggregate = round(averageEntryScore * agreementFactor)
```

Agreement factor from the coefficient of variation of prices: `cv <= 0.10 → 1.00`, `<= 0.25 → 0.92`, `<= 0.50 → 0.80`, `> 0.50 → 0.65`; one price → `0.90`.

The aggregate reports `sampleCount`, `agreement`, and reason codes.

## 4. Assessment confidence (the app's own conclusions)

For sample-based conclusions (competitor comparison, price analysis):

```
confidence = round(aggregateScore * sampleFactor)
sampleFactor = 1 sample → 0.70, 2 → 0.90, 3-4 → 0.95, >=5 → 1.00
```

For input-based conclusions (product scoring):

```
confidence = round(100 * (0.85 * basisWeight + 0.15 * freshness))
basisWeight = verified → 1.00, estimated → 0.70, guess → 0.40
caps: estimated <= 74 (medium), guess <= 45 (low)
```

## 5. Reason codes

Reason codes are language-neutral; the UI translates them.

| Code | Meaning |
| --- | --- |
| `unknown_source` | at least one entry has no stated source |
| `missing_date` | at least one entry has no observation date |
| `stale_90d` / `stale_180d` | data older than 90 / 180 days |
| `single_source` | only one source; not cross-checked |
| `small_sample` | fewer than three entries |
| `low_agreement` | price coefficient of variation above 0.50 |
| `estimated_inputs` | merchant inputs are estimates |
| `unverified_inputs` | merchant inputs are guesses |
| `no_data` | no entries |
| `high_credibility` | no negative reason found |

## 6. Model prompt contract

Any API call that asks a model to review external facts must embed this block (English version; the Chinese version is generated by `credibilityPromptBlock('zh')`):

```text
Source credibility contract (v1):
- sourceType must be one of: official_store, merchant_record, platform_search, third_party_tool, screenshot_note, unknown.
- Every external fact (competitor price, spec, sales, review) must carry sourceType, sourceNote, and observedAt (ISO date).
- Treat data as verified only when sourceType is official_store or merchant_record AND observedAt is within 30 days; otherwise call it unverified or dated.
- Never invent a source, URL, or date. If unknown, use sourceType "unknown" and say so.
- For every conclusion include confidence.score (0-100), confidence.level (high >= 75, medium >= 50, low < 50), and confidence.reasons using codes: unknown_source, missing_date, stale_90d, stale_180d, single_source, small_sample, low_agreement, estimated_inputs, unverified_inputs, no_data, high_credibility.
```

The model must return JSON only:

```json
{
  "summary": "string",
  "confidence": { "score": 0, "level": "high|medium|low", "reasons": ["string"] },
  "caveats": ["string"],
  "recommendations": ["string"]
}
```

`POST /api/intel/interpret` implements exactly this call; `lib/normalize.js` clamps and validates the response. The system message also injects today's date (`Today's date is YYYY-MM-DD.`) so the model never has to guess it when judging `observedAt`.

## 7. Integration checklist

When adding any new data source or endpoint:

1. Accept `sourceType`, `sourceNote`, `observedAt` on the input entry.
2. Run entries through `entryCredibility()`; never trust client-provided scores.
3. Summarise with `aggregateCredibility()` and report compliance with `assessmentConfidence()`.
4. Return reason codes, not prose, so the frontend can localize.
5. If the model is involved, include `credibilityPromptBlock(locale)` in the system message.
6. Add tests for fresh, unknown, stale, and single-source cases.

## 8. Versioning

`CREDIBILITY_VERSION` (currently `1`) is returned in every credibility object and exported in JSON exports. Changing weights, thresholds, or codes requires bumping the version and updating this document.
